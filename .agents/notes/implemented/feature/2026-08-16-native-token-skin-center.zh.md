# Agent Note: 原生 token 皮肤中心

Status: implemented

[English](2026-08-16-native-token-skin-center.md) | 中文

## 问题

Web 客户端原本只提供浅色、深色与跟随系统三种基础显示模式，没有产品内置的视觉变体。想使用不同调色板的用户只能依赖底层的进程内主题扩展点。直接安装社区发现页面中的任意仓库，会带来代码与素材来源、兼容性和生命周期问题，而现有主题注册表并未回答这些问题。仅在运行时应用调色板，还会让页面在客户端插件树恢复已保存选择前短暂闪过基础主题。

## 决策

`@deepseek-ai/dsh-client-ui-theme` 保留 `light`、`dark` 与 `system` 三种基础显示模式，并新增三个可持久化的内置皮肤偏好：`deep-sea`、`aurora-night` 与 `warm-paper`。深海蓝和极光夜解析为深色配色，暖纸解析为浅色配色。`system` 仍是默认值，「恢复默认」会选择它。这项决定扩展了早期[客户端设置、语言与主题分层 Agent Note](../../proposed/architecture/2026-07-25-client-settings-locale-theme.md)中的偏好列表，同时不把 DOM 所有权移出 ui-layout。

三套皮肤都是 `packages/client/ui-theme/src/builtin-themes.ts` 中的原创定义。每项定义都是冻结的语义化 `--dsw-*` token 值映射，不包含 DOM 代码、网络请求、字体、图片、样式表导入或可执行资产。一组共享的必需 token 列表覆盖构成完整皮肤的应用表面、边框、文字、业务强调色、交互、Markdown 表面、滚动条、浮层与侧栏专用别名。基础 design-platform token 会继续提供这组皮肤自有集合之外的全部语义值，包括错误、警告与成功状态颜色。

Host schema 接受全部六个内置偏好 id，因此现有 settings scope 会通过与基础模式相同的 revision 路径持久化皮肤。ThemeRuntime 在构造时注册两个基础定义与三个皮肤定义，可以立即解析已保存的皮肤。通过 `register()` 添加的动态 id 仍只存在于进程内，既不能覆盖内置 id，也不能进入 Host schema，继续遵守 [Host settings 支撑的 Web 偏好 Agent Note](../bug-fix/2026-08-06-host-backed-web-preferences.md)确定的持久化边界。

「外观」设置行呈现两个带标签的分组：三项显示模式控件和三张皮肤卡片。每张皮肤卡片会从基础表面、抬升表面、品牌色与主文字 token 中读取四个真实调色板色块，不会模仿应用截图。按钮通过 `aria-pressed` 暴露选择状态，分组标签会命名两组控件，键盘焦点保持可见，窄视口下调色板会收为单列。

Host 引导代码与 ThemeRuntime 读取同一组冻结皮肤定义。在外壳挂载前，引导代码会应用所选皮肤的配色模式、深色主题属性和全部皮肤 token。ui-layout 仍是后续 DOM 权威，并会继续按[解析后主题颜色元数据 Agent Note](2026-08-06-resolved-theme-color-metadata.md)所记录的方式，由解析后的展示结果驱动浏览器颜色元数据。

## 社区来源边界

本实现核对了官方仓库、官方 [Discussions](https://github.com/deepseek-ai/deepseek-harness/discussions) 与社区 [dsh-plugin topic](https://github.com/topics/dsh-plugin)。此次核对没有找到能够验证为可安装且兼容当前主题约定的独立主题或皮肤包。加入 GitHub topic 只是一项发现元数据，不代表官方认证。这三套皮肤没有复制任何社区包、调色板、美术素材、依赖或品牌资产。

## 验证

聚焦测试固定了扩展后的 Host schema、皮肤的持久化采用与写入、内置注册顺序、防重复保护、动态注册与资源释放、切换及恢复行为。引导测试会在外壳挂载前执行生成的脚本，并要求出现所选皮肤的全部 token 和对应配色模式。组件测试覆盖带标签的分组、`aria-pressed` 状态、仅含调色板色块的预览、延后快照选择、「恢复默认」与窄屏 CSS。皮肤完整性测试要求完整 token 名集合，拒绝 URL、导入、字体、图片、data URI 与标记载荷，并对主文字、次要文字、强调色与基础表面、前景色与强调色组合执行 WCAG 对比度门禁。

## 曾考虑的替代方案

**导入 `dsh-plugin` 下发现的主题。** 发现机制无法证明维护者身份、许可证兼容性、manifest 形态、当前约定兼容性或运行时安全。交付未经核验的包会把视觉偏好变成可执行供应链决策，因此内置皮肤只使用原创 token 数据。

**把显示模式和皮肤持久化为两项独立设置。** 这种模型会产生固定配色皮肤未曾设计或完成对比度测试的组合，还需要第二套迁移与解析规则。因此一个内置皮肤就是一个带有明确浅色或深色配色的封闭偏好；选择浅色、深色或跟随系统会退出皮肤。

**用微型应用窗口美术图作为卡片预览。** 虚构的界面缩略图会暗示调色板本身无法保证的截图或布局结果。四个具备明确语境的调色板色块可以真实预览皮肤拥有的颜色数据，也无需引入图片依赖。

**只在 ThemeRuntime 激活后应用皮肤 token。** 这样可以缩小 Host 响应，但重新加载时会出现可见的基础配色首帧。让现有同步引导代码读取同一组冻结定义，可以保持首帧与实时运行时一致。

## 后果

用户获得三项持久、无障碍的视觉选择，无需安装代码，也无需授予主题网络访问权限。设置色块、插件启动前首帧与实时运行时使用同一组定义，可以减少偏离。每套皮肤都有固定配色：操作系统变化不会改变当前皮肤，选择基础显示模式则会有意退出皮肤。每份 index 响应中的内联引导代码会增加一份有边界的产品内置字符串映射。

这项决定不会创建社区主题市场，也不会认证 GitHub topic 下的仓库。未来若支持可安装的第三方皮肤，需要明确处理来源、许可证、完整性、manifest 兼容性、审核、更新与移除的信任模型；在此之前，`register()` 与 `overrideTokens()` 仍是受信任组合使用的扩展点。
