# Agent Note: Telegram 私聊远程工作

Status: implemented

[English](2026-08-16-telegram-private-channel.md) | 中文

## 问题

桌面用户希望 Mac 在托盘中继续运行时，可以通过手机把工作交给 Harness。直接复用回环 Web API、监听局域网地址，或默认信任第一个 Telegram 发送者，都会把缺少远程认证的本机传输层变成远程执行入口。因此，这项能力需要经过认证的传输层、持久任务接纳、准确的发送者归属、明确的电脑端配对，以及 Telegram 消息无法修改的权限边界。

## 决策

**由供应商无关的 Channel 能力持有传输接纳与回传。** `@deepseek-ai/dsh-channel` 可以注册多个经过认证的供应商，但只能注册一个产品消费者。它只提供标准化文字接纳和按供应商回传，不暴露 Host RPC、设置、凭据、Shell、文件系统或公网 HTTP 路由。

**由 Agent 消费者持有持久工作语义。** `@deepseek-ai/dsh-channel-agent` 把供应商、会话与发送者的完整身份映射到本机选择的 Agent 会话。每条 Telegram 提示都带有持久的通道来源，在返回接纳结果前先刷新会话，按完整外部消息身份去重，并等待该提示对应的准确回合结束后，只回传最终 assistant 文本。`/new`、`/sessions`、`/use`、`/status`、`/stop` 与 `/help` 都在本地处理；未知斜杠命令不会进入模型。

**每条提示都使用远程安全 Agent 能力集。** 桌面组合会把通道会话固定到 `telegram-safe`：完整 persona 会关闭运行时上下文，只装配 `web_search`。创建和恢复 Agent 时会同时安装继承工具白名单与单调执行 Guard，因此本地文件、Shell、代码、凭据、设置、媒体、子代理、工作流、审批以及 Host 后续注册的工具均不可用。每条提示进入 inbox 前还会重新应用 `read-only`。Telegram 无法选择工作区、模型、预设、会话 ID 或权限。

**Telegram 是采用两步配对的纯出站供应商。** `@deepseek-ai/dsh-channel-telegram` 通过 `getUpdates` 长轮询工作，不启动任何监听端口。十分钟内单次有效的 128 位能力只会通过仅限回环地址的配对 Remote 返回，持久层只保存其哈希。用户在 Bot 私聊中打开深链后只会产生候选账号；必须回到电脑确认准确的用户数字 ID 和私聊数字 ID，候选账号才会获得授权。显示名称和用户名永远不参与授权判断。

**凭据和重放边界默认关闭。** 每次 Bot API 操作都会从 `TELEGRAM_BOT_TOKEN` 解析 Token；Token 不会进入设置、通道状态、会话消息、Remote 投影或日志。Bot 已配置 webhook、凭据缺失或轮换、Bot 身份变化、非私聊发送者或未匹配账号时都会拒绝连接。只有完成持久 Agent 接纳后才推进 Telegram 更新位置；供应商更新 ID 和 Agent 接纳在重试及重启后都保持幂等。

**绑定代际会阻止跨 Bot 重放。** 每个经电脑确认的账号都会获得新的不透明路由 epoch。Channel 会话和接纳身份使用这个 epoch，只有供应商保留回传所需的真实 Telegram chat id。因此，即使两个 Bot 看见相同的用户、私聊和消息数字，撤销并重新绑定后仍会使用新路由。停用、撤销、凭据轮换和关闭会取消并等待当前出站代际收敛。停用期间收到的消息不会被接纳。如果 Telegram 在启用校验时报告积压，提供方会保持停用，既不读取，也不确认或清空这些更新；用户可以等待 Telegram 在最长 24 小时的保留期内让它们过期，或撤销绑定、移除凭据，再绑定一个新的专用 Bot。

**持久待发队列把任务完成与传输恢复分开。** Agent 消费方会在投递前保存已完成的最终文本。出现 `CHANNEL_TELEGRAM_UNAVAILABLE` 时，系统会按指数退避持续重试，直至提供方恢复，且不会重跑模型回合。`CHANNEL_TELEGRAM_ROUTE_EXPIRED`（包括更换 Bot）和 `CHANNEL_TELEGRAM_TEXT_TOO_LONG`（包括回复需要超过三个分段）属于永久错误，会停止重试。投递采用至少一次语义：如果 Telegram 已接收一个分段，而进程在保存持久已投递标记前失败，恢复后可能重复发送该分段。

## 曾考虑的替代方案

**暴露现有 `/api` 或监听 `0.0.0.0`。** 不采用：Web 传输层的回环与来源检查不是远程认证，通用 Host 能力也远远超过手机任务控制所需范围。

**使用 Telegram 用户名或信任第一个发送者。** 不采用：用户名可选且可以变化。深链证明加电脑端核对准确数字身份，让用户能够明确决定信任对象。

**首个桌面版本使用 webhook。** 不采用：它需要一个公网可达且经过认证的 endpoint，并且与 `getUpdates` 互斥。桌面版采用出站长轮询；Bot 已经存在 webhook 时直接关闭连接。

**在 `read-only` 沙箱中暴露编程工具。** 不采用：当前只读沙箱仍允许读取文件系统，也可能读取同一用户的凭据文件。首版使用 `telegram-safe` 和执行 Guard；远程本地文件与 Shell 工作需要后续专门设计的隔离边界。

**把任意斜杠命令转发给 Harness。** 不采用：既有命令包含能力变更操作。手机通道只提供封闭的小型命令集合，未知命令会直接报错。

**让同一个绑定身份并发运行多个任务。** 首版不采用：一个身份同一时间只运行一个任务，状态、停止归属、崩溃恢复和消息顺序都更清楚。已有任务完成或停止前，第二个任务会被拒绝。

**重新启用时跳过 Telegram 积压。** 不采用：如果客户端确认积压的手机指令却不执行，用户无法发现数据已经丢失。提供方会保持停用，不触碰这些更新，直到 Telegram 让它们过期，或用户更换绑定与 Bot。

## 后果

用户可以创建专用 Bot，在本机保存 Token，生成一次性链接，在电脑端批准候选账号，然后从绑定的私聊中创建或继续 Agent 会话。关闭主窗口后，托盘会继续长轮询；明确退出应用、电脑休眠、网络中断或 Mac 关机后，手机通道都会离线。停用的通道不会消耗积压更新。如果 Telegram 在启用时报告积压，通道会保持停用，直到 Telegram 在最长 24 小时的保留期内让这些更新过期，或用户撤销绑定、移除 Token，再绑定一个新的专用 Bot。

当前是面向推理、写作和公开网页研究的文字私聊 Beta。本地文件工作、代码执行、媒体生成、群聊、附件、远程审批、任意会话 ID 和公网中继都不在范围内。Telegram Bot 聊天没有端到端加密，用户不能发送秘密。现有本机凭据提供方使用仅限账户访问的文件，不是操作系统 Keychain 边界；同一用户身份运行的原生进程仍处于信任边界内。真实手机验收需要用户自己的测试 Bot；自动化测试会使用假的 Bot API，证明配对、绑定代际隔离、私聊数字身份授权、webhook 拒绝、更新位置持久化、重试、凭据安全错误、崩溃恢复和准确结果回传。
